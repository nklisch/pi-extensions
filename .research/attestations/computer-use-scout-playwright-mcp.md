## Attested details

1. **Purpose and interaction model.** Playwright MCP is a Model Context Protocol server providing browser automation via Playwright, exposing pages to LLMs "through structured accessibility snapshots, bypassing the need for screenshots or visually-tuned models." Stated properties: "Fast and lightweight" (accessibility tree, not pixel-based input), "LLM-friendly" (no vision models needed), and "Deterministic tool application." (`README.md`, Key Features)
2. **Browser-only scope.** The tool surface is web pages in Chrome, Firefox, WebKit, or msedge channels (`--browser`); there is no desktop/native-app automation capability. Optional `--caps vision,pdf,devtools` add capabilities. (`README.md`, Configuration options table)
3. **Positioning against CLI workflows.** The README itself notes that coding agents "increasingly favor CLI–based workflows exposed as SKILLs over MCP because CLI invocations are more token-efficient," pointing coding agents at `microsoft/playwright-cli`, while MCP "remains relevant for specialized agentic loops that benefit from persistent state, rich introspection, and iterative reasoning over page structure." (`README.md`, "Playwright MCP vs Playwright CLI")
4. **Profile and isolation handling.** Three modes are documented: persistent profile (default; stored under OS cache dir `ms-playwright/mcp-{channel}-{workspace-hash}` where workspace-hash derives from the MCP client's workspace root, so different projects get separate profiles automatically); isolated mode (`--isolated`, in-memory profile, storage state lost on close, with `--storage-state` seeding); and a Chrome/Edge extension mode (`--extension`) connecting to a running browser with the user's logged-in sessions. `--user-data-dir` overrides the profile path. A persistent profile can only be used by one browser instance at a time. (`README.md`, "User profile")
5. **Local and remote execution.** The server runs locally via `npx @playwright/mcp@latest` (Node.js 18+), can run headed (default) or headless, can bind a port with SSE transport, and can connect to remote browsers via `--cdp-endpoint` or `--endpoint`. A Dockerfile is included. (`README.md`, Getting started, Configuration)
6. **File-system and network guardrails.** By default, file access is restricted to MCP workspace root directories and `file://` navigation is blocked; `--allow-unrestricted-file-access` opts out. `--allowed-origins`/`--blocked-origins` control browser request targets but the README warns these are not a security boundary and do not affect redirects. `--allowed-hosts` restricts which hosts the server serves from. (`README.md`, Configuration options table)
7. **Observability.** Options include `--console-level` for browser console messages, `--output-dir`/`--output-max-size` for output files, `--save-session` to save the session into the output directory, `--image-responses` to control image responses, `--snapshot-mode`, and `--snapshot-boxes` for bounding boxes in snapshots. Tracing is not surfaced as a CLI flag in the documented option table. (`README.md`, Configuration options table)
8. **Model coupling and sandboxing.** The server is model-agnostic: it exposes MCP tools and the client supplies the LLM; no LLM provider is configured or required by the server itself. Browser sandbox flags (`--sandbox`, `--no-sandbox`) and `--secrets` (dotenv secrets file) are supported. (`README.md`, Configuration options table)
9. **Release identity and source layout.** Package `@playwright/mcp` version `0.0.79`, Apache-2.0 license, `mcpName: io.github.microsoft/playwright-mcp`. Implementation source lives in the Playwright monorepo at `packages/playwright-core/src/tools/mcp`; this repository carries packaging, tests, and generated docs. (`package.json`; `src/README.md`)
